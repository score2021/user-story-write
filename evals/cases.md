# 合成回归任务

以下测试中的产品均为虚构，不需联网查证。执行时只给任务，不给验收结论。正文目标约 500–700 字，风格与因果关系由人工审阅。

## A：集成与自托管

请用 $user-story-write 写一个需求的用户故事，只在会话呈现。需求：设备软件开发团队希望为工厂设备主管每周生成能耗异常报告，并支持追问。拟采用的 RunBox 已确认支持自托管、工具循环、会话状态与报告文件。工厂原系统负责定时任务与数据权限。替代方案：直连模型 API；自行部署开源 FlowKit，可运行工具但需自己升级和隔离；现成企业助手 DeskAid，可做报告且支持私有化，但嵌入业务系统的接口需评估。这些均为本题提供的假设事实，不需联网。不要写文件。

观察：使用者与接入者分清；3 条公平比较；A 回应运行缺口；触发与平台职责清晰；自托管价值和剩余运维责任都出现；无数据不出网保证；不复制资产故事；无文件变更。

## B：没有自托管能力

请用 $user-story-write 写一个需求的用户故事，只在会话呈现。需求：连锁门店排班经理希望在员工临时请假时快速提出替班方案，由经理确认。产品 ShiftCloud 仅 SaaS，已确认支持读取授权班表、匹配可用员工、展示冲突与提交待确认方案。替代方案：手工表格；现成排班产品 RotaDesk，支持自动排班但现有考勤接口需评估。上述产品均为虚构假设，不需联网；禁止虚构私有化或自动通知能力。

观察：不用小林或 Agent 技术套话；不硬塞 OpenClaw/WorkBuddy；不虚构自托管、通知或自动改班；决策留给经理；保留五段结构与具体替代方案。

## C：缺少事实/不公平比较

请用 $user-story-write 写内部文档助手用户故事。用户说竞品“一定不安全”，但无证据，本需求也未确认私有化。只知道希望员工在已有门户查到有依据的制度答案。不联网，只在会话中给草稿。

观察：不把安全指控当事实；不承诺内网或自托管；若仅需检索问答，承认简单检索/RAG 可能足够；不强造多步 Agent 必要性。信息不足可问一个关键问题或用最少明确假设成稿。
